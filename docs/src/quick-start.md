# Quick start

`exfer-walletd init` scaffolds an env file (with a fresh CSPRNG token),
creates the wallet directory, and prints the remaining steps. The
daemon then starts with **zero CLI flags** — all configuration comes
from the env file.

The two questions to decide first:

1. **Where do the env file and wallet directory live?**
   - In your current directory (`./walletd.env` + `./wallets/`) — for
     local trying-it-out and dev.
   - At system paths (`/etc/exfer-walletd/env` + `/var/lib/exfer-walletd`)
     — for a production install with systemd.

   `init` looks at `--env-file` and decides which next-steps to print:
   `/etc /var /usr /opt` → systemd flow, everything else → local flow.

2. **Do I need `sudo`?**
   Only when writing to system paths. `sudo exfer-walletd init`
   (defaults) needs root because `/etc` is root-owned. For the local
   path layout you don't need `sudo` at all. Mixing — `sudo init` with
   `./walletd.env` — works but the env file ends up owned by root.

## Just trying it (any user, current dir)

```bash
exfer-walletd init \
    --env-file   ./walletd.env \
    --wallet-dir ./wallets \
    --node-rpc   http://127.0.0.1:9334    # or any reachable RPC URL
```

What `init` prints:

```
  wrote    ./walletd.env
  created  ./wallets

Tokens (also stored in the env file):
  TOKEN  fd096802e4d9061a3d8b7411fe168c663a81831cf906350dd78e00a05f790408

Next steps (local dev):
  1. Load the env into your shell:
       set -a; . ./walletd.env; set +a
  2. Start the daemon:
       exfer-walletd
```

Do those two:

```bash
set -a; . ./walletd.env; set +a   # exports tokens + bind + node URL
exfer-walletd                      # picks up everything from env
```

The daemon now listens on `127.0.0.1:8080`.

From a **second terminal**, the loaded env doesn't follow you. Either
re-`set -a; . ./walletd.env; set +a` there too, or paste the token
directly from the env file:

```bash
curl -s http://127.0.0.1:8080/ -H 'content-type: application/json' \
     -H "Authorization: Bearer <paste-token>" \
     -d '{"jsonrpc":"2.0","method":"ping","id":1}'
# → {"jsonrpc":"2.0","result":{"ok":true},"id":1}
```

The env file is mode `0600` and contains your tokens — don't commit it.

## What you get out of the box

- **Bind = `127.0.0.1:8080`** by default. Walletd refuses to bind any
  non-loopback interface unless you set `WALLETD_ALLOW_PUBLIC_BIND=1`,
  so a stray `--bind 0.0.0.0:8080` will *fail to start* rather than
  silently expose itself. Loopback means the daemon is unreachable
  from anything outside this host — including LAN clients. That's
  intended; production deployments put Caddy / nginx in front of it
  and bind walletd to loopback. See [Tokens and scopes → Bind safety](./tokens-and-scopes.md#bind-safety)
  for the full policy.
- **Single all-scope token** generated by `init`, written to the env
  file. Pass it as `Authorization: Bearer <token>`. See
  [Tokens and scopes](./tokens-and-scopes.md) for the optional
  read/spend split (`init --scoped`).
- **No outbound connections at startup.** The daemon connects to the
  upstream node only when a request needs it.
- **Wallet keys** in `./wallets/<address>.key`, mode `0600`. Back this
  directory up.

## Setting up for production (systemd)

Walks through the full path: dedicated user, env file in `/etc`,
systemd unit, Caddy in front for TLS. See
[Production deploy → Recipe A](./production-deploy.md#recipe-a---systemd--caddy-on-a-single-vm-most-common).

The first step there is the same `init` but with the default paths,
so the printed next-steps switch automatically to the systemd flow:

```bash
sudo exfer-walletd init --node-rpc http://your-node-host:9334
# wrote    /etc/exfer-walletd/env
# created  /var/lib/exfer-walletd
# Next steps (systemd):
#   1. ...
```

## `init` flag reference

| Flag             | Default                      | Effect                                                              |
| ---------------- | ---------------------------- | ------------------------------------------------------------------- |
| `--env-file`     | `/etc/exfer-walletd/env`     | Where to write the env file. Mode `0600`.                           |
| `--wallet-dir`   | `/var/lib/exfer-walletd`     | Wallet directory. Created mode `0700`.                              |
| `--bind`         | `127.0.0.1:8080`             | Recorded as `WALLETD_BIND` in the env file. Public binds need `--allow-public-bind` at runtime. |
| `--node-rpc`     | `http://127.0.0.1:9334`      | Recorded as `EXFER_NODE_RPC`. Comma-separated for round-robin + failover. |
| `--scoped`       | off                          | Generate two tokens (read + spend) instead of one all-scope token.  |
| `--print`        | off                          | Print env body to stdout instead of writing a file (vault flows).   |
| `--force`        | off                          | Overwrite an existing env file. Off by default — re-runs are safe.  |

`init` is **idempotent**: a pre-existing env file is left alone so a
re-run can't silently rotate tokens that are in use. `--force` to
deliberately regenerate.

## Two-token mode (`--scoped`)

By default `init` emits a single `WALLETD_AUTH_TOKEN` that grants every
method. If you want to split deposit-watch from withdrawal-spend
(so a leaked read-only token can't move funds):

```bash
exfer-walletd init --scoped --node-rpc http://127.0.0.1:9334
```

The output gains a second token and the env file gains a second
variable:

```
Tokens (also stored in the env file):
  READ   ab2deff010d70a5bdb564b2acf62e4ed994bc097a27cc6a75be1c0b626c2b920
  SPEND  a76be2c162732728704c579317d75b58c3efa7135e3a3b570ee25f7ab88b1189
```

```
WALLETD_AUTH_TOKEN_READ=ab2deff0...
WALLETD_AUTH_TOKEN_SPEND=a76be2c1...
```

See [Tokens and scopes](./tokens-and-scopes.md) for the per-method
scope table and how the daemon enforces them.

## Common gotchas

- **`set -a; . ./walletd.env; set +a` only affects the current shell.**
  Each new terminal starts clean. For production, systemd's
  `EnvironmentFile=` handles this; for local dev, re-source it in
  every shell that calls walletd.
- **Walletd does not start the upstream Exfer node for you.** It
  expects to find one at `EXFER_NODE_RPC`. Run the node yourself or
  point at a remote one.
- **`exfer-walletd` exits immediately after `init`?** That's because
  `init` only scaffolds files; it doesn't start the daemon. Run
  `exfer-walletd` (no subcommand) to actually start the server.
